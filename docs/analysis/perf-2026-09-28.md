# Performance review: 30 ms per 20-page chunk target (lopdf path)

This was a read-only static review. Nothing was compiled or run in Rust. The code is from worktree `tpe-wt-loop8` at HEAD `1861a55`. Line numbers come from `grep -n` on that tree. `text_cleanup.rs` was edited after the dev11 eval, so the timings are one commit older than the code.

## Scope and data used

- **Timings used.** Dev11 `report.json` for both runners, including each paper's stage timings, is in `scratchpad/eval-dev11/`. The stage means in the brief do not match dev11. I used the dev11 figures:

  | Runner | p50 ms/chunk | p95 ms/chunk | acquire | parse | order | citations | metadata (mean ms/doc) |
  | --- | --- | --- | --- | --- | --- | --- | --- |
  | ubuntu-24.04-arm | 33.8 | 109.6 | 10.0 | 48.5 | 11.7 | 3.4 | 0.2 |
  | macos-15 (Apple Silicon, closest to M1) | 30.8 | 112.6 | 14.5 | 45.2 | 12.6 | 3.1 | 0.2 |

- **What the metric counts.** The eval metric is `ms_total / chunks`, where `ms_total` is the sum of the stage timers (`eval.rs:1942-1948`). Nothing from the eval itself runs inside the timed path:
  - `latex_refs::ground_truth` runs before `run_job` (`main.rs:798`).
  - `eval::evaluate` runs after it.
  - Chunk hashing (`pipeline.rs:317`) and dropping the lopdf `Document` both happen outside the stage timers.

  Speeding up those untimed parts would show in `tpe bench` wall time, not in the eval number. A paper under 20 pages is one chunk, so its whole-document time counts as one chunk.

- **Where the time goes at p50.** For the 19 arm papers between 28 and 40 ms/chunk: parse is 63%, order 19%, acquire 12%, citations 5%, metadata ~0%. On macOS (13 papers): parse 56%, order 22%, acquire 17%, citations 5%. So parse decides p50 and acquire matters more on macOS.
- **Median cost per page (arm).** acquire 0.17 ms, parse 1.32 ms, order 0.45 ms, citations 0.10 ms.

## Parse cost model (fitted over the whole dev corpus)

`scratchpad/fitparse.py` inflates every content and Form stream of each cached dev PDF. It counts operator tokens, shown strings (`Tj`/`TJ`) and file size, then fits least squares to the arm `parse_ms`. Fonts, images, object streams, xref and cmaps are left out.

```
parse_ms ≈ 0.47 ms/page + 0.457 µs per content operator + 0.58 µs per Tj/TJ + 0.40 ms per MB of file
n = 59 (2601.09974 excluded), R² = 0.85
```

- The median paper has 1,267 operators and 190 shown strings per page.
- For the median paper, the per-operator term alone explains 47% of parse time.
- Most operators are path construction and painting (`m l c re f S …`), which the text extractor ignores. They still go through lopdf's `Content::decode`, which allocates one `Operation { operator: String, operands: Vec<Object> }` per operator. It uses a nom `alt` that tries inline image, null, boolean, real and integer on every token (`lopdf-0.45.0/src/parser/mod.rs:684-721`).
- This is the largest single cost.

## Ranked top 10 (by expected p50 impact)

"Est." values are guesses unless marked *fitted* or *measured*. The simulated p50/p95 (bottom section) applies the stage cuts listed there to every paper's dev11 stage timings.

### 1. Content streams are fully decoded into `Vec<Operation>`, path operators included (parse)

- **Where:**
  - `lopdf_backend.rs:1267-1268`: `doc.get_page_content` then `Content::decode`, once per page.
  - `lopdf_backend.rs:1205-1209`: Form XObjects. These are cached per stream id (good), but still fully decoded once.
  - The interpreter `run` (`lopdf_backend.rs:888`) then matches `op.operator.as_str()` on every operator.
- **Evidence:**
  - *Fitted:* 0.457 µs per operator.
  - Vector-heavy outliers: 2309.10334 has 257k Form operators and only 561 text shows, and parses in 124 ms for 11 pages. 2501.17300 has 368k Form operators and parses in 215 ms.
- **Change:** write a streaming content lexer (about 300 lines).
  - Work on the byte slice directly and keep operands in a small reused stack (`SmallVec<[Operand; 6]>` of borrowed slices and numbers).
  - Materialise operands only for the operators `run` handles: `q Q cm BT Tf Td TD Tm T* TL Tc Tw Tz Ts Tj ' " TJ Do`.
  - For every other operator, clear the stack without allocating.
  - Skip inline images by scanning for `EI`.
  - Cache Form XObjects as the lexed "text-relevant op list", not the full `Vec<Operation>`.
  - Cheaper interim step: before decoding a Form, `memchr`-search its bytes. If they contain no `BT`/`Tj` and no `Do`, cache it as empty and skip decoding. This catches pure-vector plots only.
- **Est.** (guess: 60% of the per-operator cost removed):
  - arm p50 **34.0 → 28.2** and p95 109.6 → 68.
  - macOS p50 30.8 → 25.8.
  - 2309.10334 would drop from ~125 to ~50 ms, 2501.17300 from ~215 to ~95 ms.

### 2. No release profile: `codegen-units = 16`, no LTO (all stages)

- **Where:** `Cargo.toml` has no `[profile.release]`.
- **Change:**
  ```toml
  [profile.release]
  lto = "fat"
  codegen-units = 1
  ```
  Optionally add `panic = "abort"`, but only if `catch_unwind` in `main.rs:361` isn't needed. It is needed, so keep unwind.
  - Cross-crate inlining matters most for lopdf's nom parser and for `regex`.
  - The cost is CI build time only.
- **Est.** (guess, a typical 5–10%): p50 34.0 → 31.7 alone. There is no code risk.

### 3. SHA-256 of the whole file on acquire runs at software speed (acquire)

- **Where:** `acquire.rs:108` `fs::read`, then `acquire.rs:117` `sha256_hex(&bytes)`, which calls `schema.rs:301`. That uses `sha2 0.10.9`.
- **Evidence** (*measured* throughput, acquire_ms against file size):

  | Paper | Size | acquire (arm) | Throughput |
  | --- | --- | --- | --- |
  | 2412.11061 | 54.2 MB | 147.8 ms | ≈ 367 MB/s |
  | 2509.12458 | 17.6 MB | 45.7 ms | ≈ 386 MB/s |
  | 2604.03540 | 8.2 MB | 21.2 ms | ≈ 395 MB/s |

  - macOS gives ~265 MB/s.
  - That rate is software SHA-256. ARMv8 SHA2 instructions give roughly 1.5–2 GB/s.
  - The cause is unverified. It is probably that sha2 0.10 enables the aarch64 intrinsics only behind a crate feature. Check with `cargo tree -e features -i sha2@0.10.9` and the crate's `cfg_if` in CI.
- **Change** (either or both):
  - (a) Move to `sha2 = "0.11"`. It is already built for lopdf (see `Cargo.lock`), so no new crate is added. Confirm it picks the hardware backend, or enable the 0.10 feature that does.
  - (b) Hash on a scoped thread while `Document::load_mem` parses. `std::thread::scope` in `pipeline.rs:183-188` would do it. This hides the hash from wall time however the backend question comes out.
  - The file read itself (page cache memcpy, ~5–10 GB/s) is not the problem.
  - Hashing lazily is not an option: the hash is the document identity (`Document.hash`).
- **Est.:**
  - acquire ×0.3: arm p50 34.0 → 32.7, p95 109.6 → 92.9.
  - macOS p50 30.8 → **27.3**. Acquire is 17% of the macOS p50 band, so this is the second-biggest macOS win.
  - 2412.11061 would go from 187 to ~85 ms/chunk.

### 4. `superscript_target` is O(lines² × spans) per page (order)

- **Where:**
  - `text_cleanup.rs:774-800`, called for every body line from `merge_scripts` (`text_cleanup.rs:912-919`).
  - For every line whose text has a script form (every short numeric line: table cells, equation numbers, axis ticks), it loops over all lines of the page.
  - For each of those lines it calls `baseline_of(page, other)` (`text_cleanup.rs:749`), which calls `line_size` (`text_cleanup.rs:290`). That walks the line's spans with `span.text.trim()`, twice.
  - Each candidate also runs `script_form` twice, allocating two Strings.
- **Evidence:** table-heavy pages. 2412.11061 has 151 and 108 table-text lines on pages 12–13. A 300-line page with ~150 numeric lines means ~45k `baseline_of` calls.
- **Change:**
  - Precompute per page, once: `Vec<Option<LineGeom { bbox, baseline, size, column }>>`.
  - After a merge, recompute only the target line's entry. The merged fragment is smaller, so the dominant size is unchanged.
  - Keep the lines' indices sorted by baseline and binary-search the window `[bbox.y0 - RAISED_HIGH*max_size, bbox.y0 - LOWERED_LOW*max_size]`, so each candidate looks only at nearby rows.
  - Apply the same cache in `script_target` (`text_cleanup.rs:569`), which also calls `line_size` per neighbour.
- **Est.** (guess): 5–10× less time in `merge_scripts`. Together with #5, about −25% of order (p50 −1.9 ms for #4+#5 together).

### 5. `xy_cut` re-sorts the same index set up to 5× per node and allocates per node (order)

- **Where:** `reading_order.rs:906-949`. Per node:
  - `column_cut` sorts left-first (`:807`).
  - `spanning_row_cut` sorts top-first (`:738`) and allocates `Vec<bool>` in `margin_runs` (`:719`).
  - `row_cut` sorts again (`:700`).
  - In the other branch, `masked_column_cut` sorts (`:750`), copies (`:755`) and re-sorts through `column_cut`.
  - `rows_read_first` allocates four partition Vecs (`:867-869`).
  - When no row cut is found, `column_cut` runs again with an identical result.
  - The leaf sorts once more (`:948`).
- **Evidence:** the cuts take the widest gap, so the recursion is unbalanced (depth ≈ number of blocks). That makes the cost O(n² log n) in the worst case.
- **Change:**
  - Sort once at the root in both orders (`by_top`, `by_left`).
  - When splitting, partition both lists stably with a membership bitmap. That is O(n) and needs no re-sort.
  - Reuse the first `column_cut` result instead of calling it again.
  - Pass `margin_runs` a reusable scratch buffer.
- **Est.** (guess): −20–40% of the XY-cut share of `order_page`. Counted in #4's −25%.

### 6. Form and page streams are inflated with `miniz_oxide`, unless another crate already enables `zlib-rs` (parse)

- **Where:** lopdf `Stream::decompressed_content` / `get_plain_content`, called from `lopdf_backend.rs:1205` and `document.rs:598` inside `get_page_content`.
  - `Cargo.lock` lists both `miniz_oxide` and `zlib-rs` under `flate2`, but the lockfile doesn't show which feature is active. Verify with `cargo tree -e features -i flate2`.
- **Change:** in `Cargo.toml`:
  ```toml
  flate2 = { version = "1", default-features = false, features = ["zlib-rs"] }
  ```
  Feature unification switches lopdf's inflate too.
- **Est.** (guess: 1.2 ms saved per inflated MB): p50 −0.2 ms, p95 −0.5 ms. 2309.10334 and 2501.17300 would each save 7–11 ms.

### 7. First-document warm-up: ~95 lazily compiled regexes plus rayon pool start (citations and parse)

- **Where:**
  - 76 `Regex::new` in `citations.rs`, 15 in `metadata.rs` and 7 in `text_cleanup.rs`. All are inside `OnceLock::get_or_init` (checked), so none is compiled per call.
  - The large Unicode ones (`narrative_marker_re` at `citations.rs:683`, `clause_scan_re`, `author_year_signature_re`) compile on their first match.
  - The lopdf default feature `rayon` starts the global pool on the first `load_mem`.
- **Evidence** (*measured*):
  - The first paper in every run is 2108.04588. Its citations take 31–48 ms, against a typical 1–3 ms.
  - The second paper's citations take 8–15 ms.
  - The first paper's parse is ~60 ms on both platforms, against the 0.47 ms/page + ops model.
- **Change:** add `pipeline::warm_up()`.
  - It forces every regex accessor (a single `static REGEXES: LazyLock<Regexes>` makes this one call) and runs a one-page dummy `load_mem`.
  - Call it once at startup in `eval`, `bench`, `extract` and the future service.
  - It must stay outside `run_job` timing.
- **Est.:** p50 and p95 barely move. 2108.04588 would go from 57 to ~40 ms/chunk. This removes a cold-start penalty of ~30–45 ms per process that the service would see.

### 8. Font decoding: `/W` lookup is a linear scan, and ToUnicode decoding allocates per glyph (parse; matters for XeLaTeX/LuaLaTeX/Word PDFs)

- **Where:**
  - `CompositeWidths::width` (`lopdf_backend.rs:401-402`) scans every `/W` range for every glyph. `parse_w_array` (`:659`) expands `c [w1 … wn]` into n single-code ranges, so the cost is O(glyphs × widths).
  - `Decode::UnicodeMap` goes through `Document::decode_text` (`decode_with`, `:1062`). In lopdf `encodings/mod.rs:84-117`, each code gets a `Vec<u16>` from `ToUnicodeCMap::get` (`cmap.rs:148`), is appended, rebuilt as UTF-16BE bytes and decoded with `encoding_rs`.
- **Change:**
  - At font load (already cached per font id in `SessionCache`), turn `/W` into a sorted `Vec<(first, last, w)>` searched with `binary_search_by`. Or, for fonts with fewer than about 8k CIDs, build a dense `Vec<f32>` indexed by CID.
  - Memoise ToUnicode per font:
    - If the codespace is 1 byte, build a 256-entry table like `ByteTable`.
    - For 2 bytes, fill a `HashMap<u16, Box<str>>` lazily.
- **Est.:** small on this dev set, since most papers are pdfTeX Type1 with `/Differences` and already use `ByteTable`. Large on Type0-heavy corpora: 1k widths × 3k glyphs/page is ~3M comparisons, about 1–3 ms per page.
- **Unknown:** this may be part of the unexplained 2601.09974 (see below).

### 9. Allocation per span and per line in backend, grouping and cleanup (parse and order)

- **Where:**
  - `lopdf_backend.rs:1019`: `font.base_font.clone()` allocates a String for every emitted span.
  - `:1051`, `:1056`, `:1077`, `:1097`, `:1103`: `warn(format!(…))` builds a label and a message for every shown string on Latin-1, undecodable or unmapped fonts, then `Vec::contains` (`:871`).
  - `reading_order.rs:484`: every span's text is cloned into `pieces`. `:539` does `text.trim().to_string()`.
  - `schema.rs:77-78`: `default_line_role()` allocates `"body"` per line.
  - `text_cleanup.rs:420`: `separators` allocates a String per line (almost always `"\n"`).
- **Change:**
  - Store the span font name as `Rc<str>`/`Arc<str>`, or intern a font id. Serde output stays the same string.
  - Keep a per-font "warned" flag in `LoadedFont` or a `HashSet<ObjectId>` so each message is formatted once.
  - In `finish_line`, borrow `&str` and copy only pieces that get accent marks (`Cow`).
  - Trim in place.
  - Make `role` a `&'static str` or a `Cow<'static, str>`.
  - Store separators as byte ranges into `page.text`.
- **Est.** (guess): 2–4% of parse+order at p50 (~0.5–1 ms/chunk).

### 10. Whole-document passes that run twice or allocate per word (order and citations)

- **Where:**
  - `vocabulary()` (`text_cleanup.rs:934-980`) makes three `Vec` collects per token, plus `word.to_lowercase()` and a `BTreeSet<String>` insert per word (`:968`). It also does `format!` per compound (`:976`). That is about 8–12k allocations per paper.
  - `find_reference_sections(pages)` runs twice per document: in `extract_citations` (`citations.rs:4339`) and again inside `find_citation_markers` (`:4270`).
- **Change:**
  - Collect the hyphen join candidates first (usually fewer than 50). With none, skip `vocabulary`. Otherwise use `HashSet<Box<str>>` with a fast hasher, lower-case into one reused buffer and insert only when absent. Iterate the splits without collecting.
  - Pass `sections` into `find_citation_markers`.
- **Est.** (guess): 0.5–2 ms per paper, <0.1 ms/page, and a small cut to citations.

**Not in the top 10, but noted:**
- `Document::load_mem` parses every object eagerly, in parallel through rayon, and copies every stream's raw bytes, images and font programs included. 2412.11061 (54 MB, 13 pages) still takes 33 ms to parse because of this.
- Fixing it needs lopdf changes: lazy object loading, or a `LoadOptions` filter that drops `/Image` and `/FontFile*` contents before the copy. That is worth a follow-up once #1 lands.

## Suspects from the brief: checked and not a cost

- **Regexes built per call:** none. Every `Regex::new` in `citations.rs`, `metadata.rs` and `text_cleanup.rs` is inside `OnceLock` (see #7 for the one-off cost).
- **`chars().nth`:** one use, `citations.rs:2690` `token.chars().nth(1)`, which is O(1).
- **`regex.replace_all` over page text:** none. `replace_all` appears only in `metadata.rs:1103-1104, 1280, 2546`, on author-name strings.
- **Repeated `find` in O(n²) patterns:**
  - `find_citation_markers` computes char offsets with a running cursor, so it is linear (`citations.rs:4317-4330`).
  - `locate` in `text_cleanup.rs` runs per span of one target line.
  - `regions.rs` does per-caption `band_entries` sorts, and pages have few captions.
- **Per-page whole-document scans in cleanup:**
  - `mark_furniture` is one document pass into a `BTreeMap`. Not quadratic.
  - The only quadratic loop is per page (#4).
- **`group_lines`:** `find_line` stops early on the baseline window. The accent searches use `partition_point`. Fine.
- **lopdf per-page object parsing:**
  - The document is parsed once in `open`. Fonts (with `ByteTable`) and Form XObjects are cached per `ObjectId` in `SessionCache`.
  - Per page there is only `get_page_content` (inflate) and `Content::decode` (#1, #6).
- **`eval.rs`:** nothing in the timed path (confirmed above).

### 2601.09974: unexplained, needs a CI profile

- 30 pages, 1.4 MB, 56k operators and 6.3k shown strings. The model predicts 46 ms of parse. The measured 198 ms is the same in every run (dev8–dev11: 196–198 ms).
- It is not a lopdf-only problem:
  - pdfium takes **1,135 ms** to parse this file and docling-text 504 ms (`native-art` arm dumps).
  - For comparison, 2309.10334 takes 177 ms with pdfium, and 2511.13979 (also produced by pikepdf) 68 ms.
- So the cost is in the file itself. Its features:
  - 8 Type3 fonts.
  - 27 ToUnicode CMaps, most of them on fonts without `/Encoding`, so #8's `UnicodeMap` path.
  - ~644 small content-like streams (median 54 bytes), probably Type3 CharProcs and appearance streams.
- None of these explains 4× on its own. Suggested one-off: `cargo flamegraph` or `perf record` on `tpe bench --iterations 20` for this file in CI.
